## 2. Settings store — plan

Agreed on the reasoning, and it is the right call: a hardcoded shop header means the owner cannot
fix a typo in his own shop name without a code change and a redeploy, and at that point he is
dependent on us for a five-second edit.

### Single-row, typed columns — not key-value

You offered either. **Single row**, and the reason is the receipt:

| | Single row (chosen) | Key-value |
|---|---|---|
| Read for the receipt | **1 query**, 3 typed fields | 1 query, then find each key in the result |
| Types | `shopName` is a string, enforced by the column | every value is `TEXT`; a future `receiptFooterEnabled` becomes `"true"` and someone parses it |
| A missing field | `null` — visible in the type | key absent — silently `undefined` at a call site |
| Adding a field later | a migration | no migration |

Key-value only wins on "no migration to add a field", and this app has a controlled migration
process anyway (nothing here runs without your go). Typed columns are worth more than that. It
still generalises exactly as you want — future owner-editable settings become columns on the same
row, and the screen grows a section.

### The model

```prisma
/// Owner-editable app settings. EXACTLY ONE ROW, id = "app".
///
/// The home for anything the owner must be able to change without a redeploy —
/// starting with the receipt header. Not a config file, deliberately: a typo in
/// the shop name should be a 5-second edit on his phone, not a deploy.
model Settings {
  id          String   @id @default("app")
  shopName    String?
  shopPhone   String?
  shopAddress String?
  updatedAt   DateTime @updatedAt
}
```

Three decisions inside that, each with a reason:

- **`id` defaults to `"app"`, and the migration adds a CHECK constraint pinning it.** The singleton
  is then a database guarantee, not a convention someone can break with a second `create()`. Every
  read is `findUnique({ where: { id: "app" } })` — no "get the first row" ordering ambiguity.
- **All three fields nullable, not `@default("")`.** An empty string and "not set yet" are different
  facts, and the receipt needs to tell them apart to decide between printing a header and printing
  a placeholder. Non-empty is enforced at the *save* boundary by zod, where a real message can be
  shown, rather than by a column default that quietly makes blank look intentional.
- **`updatedAt` with no DB default.** Prisma sets it on every write; the migration's seed INSERT
  supplies `now()` explicitly (it is `NOT NULL`, so it must — that is the one thing a bare
  `INSERT (id)` would fail on).

### The migration SQL

**Generated by the real Prisma 6 CLI** — `npx prisma migrate diff --from-schema-datamodel
prisma/schema.prisma --to-schema-datamodel <schema + Settings> --script`, verified
`prisma 6.19.3 / @prisma/client 6.19.3`. Datamodel-to-datamodel, so **no database was contacted to
produce it**. The `CREATE TABLE` below is the CLI's output verbatim; the three statements after it
are added by hand for the reasons given.

**Proposed path:** `prisma/migrations/20260810120000_add_settings/migration.sql`

```sql
-- CreateTable
CREATE TABLE "Settings" (
    "id" TEXT NOT NULL DEFAULT 'app',
    "shopName" TEXT,
    "shopPhone" TEXT,
    "shopAddress" TEXT,
    "updatedAt" TIMESTAMP(3) NOT NULL,

    CONSTRAINT "Settings_pkey" PRIMARY KEY ("id")
);

-- Singleton, enforced by the database rather than by convention.
-- Without this, a stray create() silently gives the app two settings rows and
-- the receipt starts depending on which one is read first.
ALTER TABLE "Settings"
  ADD CONSTRAINT "Settings_singleton_check" CHECK ("id" = 'app');

-- Seed the one row so every read finds it. GET never has to handle "no row
-- yet", and save is a plain UPDATE rather than an upsert that could race.
-- updatedAt is NOT NULL with no default, so it must be supplied here.
INSERT INTO "Settings" ("id", "updatedAt") VALUES ('app', now());

-- RLS: REQUIRED for every new table (see "Database security" in CLAUDE.md).
-- Prisma does not manage RLS, so migrate would otherwise create this table with
-- RLS OFF and expose it through PostgREST to the public anon key. Default deny,
-- zero policies — same as the other 17 tables. Prisma is unaffected: it connects
-- as postgres, which both owns the table and has rolbypassrls.
ALTER TABLE public."Settings" ENABLE ROW LEVEL SECURITY;
```

**After running it I would verify, not assume:**
`relrowsecurity = true` / `relforcerowsecurity = false` on `Settings`, exactly one row present, the
CHECK constraint rejecting a second id, and `get_advisors({ type: "security" })` reporting
**18 × `rls_enabled_no_policy` at INFO** — up from 17, with **no** `rls_disabled_in_public` at
ERROR. That advisor delta is the actual proof the RLS line worked.

### The screen and the route (built after the migration, on your go)

- **`/settings`** — one card, three fields, Save. **Neutral zinc**, not a module accent: it is
  app-level, and the Design System's rule is one accent per screen, none of which apply here.
  Nav entry alongside the modules.
- **`GET` + `PATCH /api/settings`** — `runtime = "nodejs"`, `requireOwner()` first, zod-validated
  body, `{ data, error }` envelope, friendly error mapping. No Decimals involved, so no serializer
  needed. Save is `update({ where: { id: "app" } })`.
- **Validation:** `shopName` required and non-empty *to save* (the receipt's whole purpose), phone
  and address optional. Trim on the way in.
- **Query budget:** reading settings is **one round trip ≈ 1.1s** on the current
  Washington-DC-to-Seoul setup (CHECKLIST #14). For the receipt, fetch it in the **same handler**
  as the sale rather than as a separate client request, so the printout costs one extra query and
  not an extra request; and it is a strong candidate for caching, since it changes roughly never.
  Worth deciding when we do part (b).
