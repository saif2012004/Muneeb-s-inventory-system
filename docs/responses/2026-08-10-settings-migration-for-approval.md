## 1. The schema

```prisma
/// Owner-editable app settings. EXACTLY ONE ROW, id = "app".
///
/// The home for anything the owner must be able to change without a redeploy —
/// starting with the receipt header. Not a config file, deliberately: a typo in
/// the shop name should be a 5-second edit on his phone, not a deploy.
///
/// SEEDED WITH DELIBERATELY UNMISTAKABLE PLACEHOLDERS. A receipt printed before
/// setup must read as obviously unconfigured, never as plausibly real — see the
/// note on `configuredAt`.
model Settings {
  id           String    @id @default("app")
  shopName     String
  shopPhone    String?
  shopAddress  String?
  /// NULL until the owner saves his real details for the first time.
  /// This is the go-live check (CHECKLIST #2b), and it is a recorded FACT rather
  /// than a string comparison against the placeholder text — which would stop
  /// detecting anything the day someone edits that text.
  configuredAt DateTime?
  updatedAt    DateTime  @updatedAt
}
```

**`shopName` is NOT NULL; phone and address are nullable.** With placeholders seeded there is always
a name to print, so the receipt never needs a `?? fallback` on the one line it cannot go without.
Phone and address stay nullable because **"the shop has no phone" is a legitimate final state** —
distinct from "not set yet" — and the receipt should be able to omit the line rather than print an
empty one.

**`id` defaults to `"app"` and is pinned by a CHECK constraint** (in the SQL below), so the singleton
is a database guarantee rather than a convention a stray `create()` can break. Every read is
`findUnique({ where: { id: "app" } })` — no "take the first row" ordering ambiguity.

## 2. The one thing I'd like you to actually decide: `configuredAt`

You asked for two things that pull in the same direction — the checklist must catch unconfigured
placeholders at handoff, and the Settings screen must visibly flag them. Both need to answer *"has
the owner set his real details yet?"*, and there are two ways to answer it:

| | **Compare against the placeholder strings** | **`configuredAt` column (proposed)** |
|---|---|---|
| How it works | `shopName === "SET SHOP NAME IN SETTINGS"` | `configuredAt === null` |
| Cost | no extra column | one nullable column |
| Fails when | someone edits the placeholder wording — every already-seeded row silently stops being detected, and the flag quietly goes away | — |
| Handoff check | eyeball the screen, or hardcode the string into a SQL query | `SELECT "configuredAt" FROM "Settings"` — unambiguous |
| Owner types the placeholder text himself | false positive | correctly reads as configured |

I've included it because the go-live check is the whole point of the item, and a check that can
silently stop working is worse than no check — it reports "configured" for a shop that isn't. **It
is one nullable column in an additive migration and it is trivial to drop** if you'd rather not
carry it: say so and I'll remove the column and the `NULL` from the INSERT, and the flag becomes a
string comparison.

The rest of the design is exactly as we agreed.

prisma/schema.prisma --to-schema-datamodel <schema + Settings> --script`, on `prisma 6.19.3` /
`@prisma/client 6.19.3`. Datamodel-to-datamodel, so **no database was contacted to produce it**. The

for a stated reason.

**Proposed path:** `prisma/migrations/20260810120000_add_settings/migration.sql`

```sql
-- CreateTable
CREATE TABLE "Settings" (
    "id" TEXT NOT NULL DEFAULT 'app',
    "shopName" TEXT NOT NULL,
    "shopPhone" TEXT,
    "shopAddress" TEXT,
    "configuredAt" TIMESTAMP(3),
    "updatedAt" TIMESTAMP(3) NOT NULL,

    CONSTRAINT "Settings_pkey" PRIMARY KEY ("id")
);

-- Singleton, enforced by the DATABASE rather than by convention. Without this a
-- stray create() silently gives the app two settings rows, and the receipt then
-- depends on which one happens to be read first.
ALTER TABLE "Settings"
  ADD CONSTRAINT "Settings_singleton_check" CHECK ("id" = 'app');

-- Seed the one row, with placeholders that CANNOT be mistaken for real shop
-- details. A receipt printed before setup must be obviously unconfigured — a
-- friendly "Your Shop Name" would print something that looks finished and is
-- wrong, and the customer walks away holding it.
--
-- configuredAt stays NULL: the owner has not set anything yet, and that is the
-- fact the go-live check reads (CHECKLIST #2b).
-- updatedAt is NOT NULL with no DB default, so it must be supplied here.
INSERT INTO "Settings" ("id", "shopName", "shopPhone", "shopAddress", "configuredAt", "updatedAt")
VALUES (
  'app',
  'SET SHOP NAME IN SETTINGS',
  'SET PHONE IN SETTINGS',
  'SET ADDRESS IN SETTINGS',
  NULL,
  now()
);

-- RLS: REQUIRED on every new table (see "Database security" in CLAUDE.md).
-- Prisma does not manage RLS, so migrate would otherwise create this table with
-- RLS OFF and expose it through PostgREST to the public anon key. Default deny,
-- zero policies — same as the other 17 tables. Prisma is unaffected: it connects
-- as postgres, which both OWNS the table and has rolbypassrls.
ALTER TABLE public."Settings" ENABLE ROW LEVEL SECURITY;
```

### What I will verify after running it — four checks, not a glance

1. **RLS actually on:** `relrowsecurity = true` **and** `relforcerowsecurity = false` on `Settings`
   (`FORCE` would apply RLS to the owner too and break Prisma).
2. **The advisor delta:** `get_advisors({ type: "security" })` reports **18 ×
   `rls_enabled_no_policy` at INFO**, up from 17, with **no `rls_disabled_in_public` at ERROR**.
   That delta is the actual proof the RLS line took effect — the healthy steady state, not a
   regression.
3. **Exactly one row**, holding the placeholders, with `configuredAt IS NULL`.
4. **The singleton constraint bites:** an `INSERT … VALUES ('other', …)` is rejected. Verified and
   rolled back, not left behind.

### Risk

Low, and bounded: a new table, no data to migrate, no reconciliation, nothing reads it yet, and
`DROP TABLE "Settings";` reverses it completely. It is independent of the unified-sale work.
It is still a live-DB migration, so it waits for your go.
