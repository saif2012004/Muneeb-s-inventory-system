## What the app looks like now

**One till.** `/sales/new` rings every bill; `/sales` lists, edits and prints them. The sidebar went
from eight entries to seven, and the mobile bottom bar swapped its two dead tabs for **Sales** and
**Customers** — the two screens you'd actually reach for with a thumb.

**The Shop filter is the replacement for the two deleted screens**, and it works the way a mixed
bill demands: it matches a sale with **at least one line** in that shop. A bill holding Pepsi and
milk shows up under both, because it genuinely is both. Filtering to "every line" would have hidden
it from each and quietly understated what both shops sold.

Verified in the browser: **Bakery → Rs. 5,000 · Milk → Rs. 6,000 · Beverages → none · All → both.**

## Reading one table instead of four made a lot of code disappear

| | Before | Now |
|---|---|---|
| `getCustomerBalance` | 5 queries + a raw statement | **2** |
| `getCustomerBalances` | 5 | **2** |
| `getTotalOutstanding` | 5 | **2** |
| `getCustomerActivity` | 4 + a JS de-duplication pass | **2** |
| Reports trend / top products / product sales | `UNION ALL` across 2–4 sources | one scan each |

**`notAMigrationCopy()` is gone.** Every sum over `Sale` used to carry a `NOT EXISTS` against three
tables, because the migrations copied your bills into `Sale` keeping their ids — so each existed
twice and anything reading both counted it twice. With one copy left, it matches nothing.

That filter also had to exist in **two forms** — SQL on the balance paths, JavaScript on the profile
— and the two disagreeing is not hypothetical: right after S5 your profile listed the same milk sale
twice while the balance beside it stayed right. That whole class of bug is now impossible.

**Net: 5,003 lines deleted, 549 added.**

## 🔴 A live bug found and fixed on the way

**`lib/catalog-guards.ts` checked only the old item tables** — which stopped being the truth the day
the till shipped (S4.2). A product sold *only* on the till read as having **no sale history**, so
deleting it was attempted as a **hard** delete, and the foreign key turned what should have been a
polite "deactivate it instead" into a 500. It now reads `SaleItem`.

Two smaller wins: **top-products finally works for milk** (there was never a milk item table to
scan, so it always came back empty), and the removed CSV types now 400 with a message naming the
valid ones instead of downloading an empty file.
